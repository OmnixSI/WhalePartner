# 0.3.4 性能记录

## #149 语音启动

**测什么：** 从打开 App 到语音模式可以开始录音的时间。

**改了什么：** X-ASR 的流式模型和整句精修模型并行载入；启动时先预热 X-ASR，结束后再预热 CosyVoice；模型载入完成后立即进入录音，不再多等一个状态轮询间隔。

**结果：**

| 场景 | 之前 | 之后 |
|---|---|---|
| 冷启动 | 6.00 秒 | 4.66 秒 |
| 热启动 | 3.31 秒 | 2.56 秒 |

**代价：** 预热顺序改成先 X-ASR、后 CosyVoice，所以 TTS（语音合成）就绪变晚，热启动约 3.7–4.1 秒。

## #117 聊天响应

**测试条件：**
- 隔离实例：独立数据目录，不碰日常使用的数据。
- 同一组 6 句话，依次发送，走 Codex 链路，模型 `gpt-6-luna`，推理档位 `low`。
- 前后各测一次，用同一批提示词；数据来自实例日志里的 `[chat-perf]`、`[codex-perf]` 行和请求端计时。
- 另有一次前测混进了测试数据目录里留下的旧状态（冷启动首字 8.5 秒、召回 1.5 秒），数据不干净，已弃用并重测。

**结果：**

| 指标 | 之前 | 之后 |
|---|---|---|
| 首字，中位数 | 3.87 秒 | 2.70 秒 |
| 完整回复，中位数 | 4.37 秒 | 3.17 秒 |
| 冷启动后第一句的首字 | 5.62 秒 | 2.90 秒 |
| 打开 App 到第一句的首字 | 6.15 秒 | 3.41 秒 |
| 记忆召回，中位数 | 958 ms | 13 ms |
| 每轮输入 token | 23.5k | 11.6k |

**瓶颈和对应的改动：**
1. **mem0 遥测。** mem0ai 的 search / getAll / add 都会先等一次遥测 id 的读写，被抽中时还要同步等一个发往 PostHog 的请求（悉尼实测 1–1.4 秒），聊天首字前的召回被它拖住。现在加载 mem0ai 之前设 `MEM0_TELEMETRY=false`，召回中位数从 958 ms 降到 13 ms。
2. **Codex 多带的工具定义。** 聊天只用 Codex 生成文字，不需要它的编码工具，但默认每轮要带约 2 万 token 的工具定义。聊天用的 Codex 子进程现在关掉 shell、浏览器、web_search 等工具，只作用于这个子进程，不改 `~/.codex/config.toml`。每轮输入 token 从 23.5k 降到 11.6k。
3. **Codex 进程冷启动。** 第一句话原来要等约 0.85 秒的进程启动和模型列表。现在后端启动后先拉起 Codex 服务并取一次模型列表（不发模型请求、不耗额度），冷启动后第一句的首字从 5.62 秒降到 2.90 秒。

## 分段耗时日志

后端每轮聊天会在日志里写两行，之后排查慢的原因先看它们：

- `[chat-perf]`：`recallMs`（记忆召回）、`contextMs`（拼好上下文）、`contextChars`、`firstDeltaMs`（首字）、`replyMs`（完整回复）、`provider`。
- `[codex-perf]`：`coldStart`（是否刚拉起进程）、`threadStartMs`、`turnStartMs`、`firstDeltaMs`、`totalMs`、`inputTokens`、`cachedInputTokens`、`promptChars`；另有 `stage: "models"` 一行记录模型列表耗时。

日志位置见 README 的「排错」一节。

## 局限

- #117 的数字来自一台机器上的一次前测和一次后测，每组 6 句；单句首字波动可达一两秒（后测第 2 句就是 5.3 秒），方向可信，小数位不要当精确值。
- 网络状况会影响 Codex 首字，不同时段的绝对值会不同。
- #149 的数字是打开 App 到语音可用的墙钟时间，只在本机测过。
